# PRODUCT-SWAP PLAYBOOK — Fixetta ("ASCEND") ecom-arbitrage

**Status:** DRAFT — for manager review only. Not published. Not deployed.
**Owner:** Fixetta operator (one Medusa v2 backend, two intended sub-brands)
**Last updated:** 2026-09-11

---

## 0. Purpose & scope

This playbook documents how one operator swaps a **niche / product set** in and out of
the Fixetta store fast on the **single Medusa backend**, running the *"test products until
a hit"* loop. A "product set" today is a small catalog (currently **4 live men's products**)
that must be mirrored across **six places** before it is truly live. Miss any one and the
swap silently breaks (usually the live-merge, an image 404, or a stale prerender).

The store has **two environments** (driven by env vars, `app/src/lib/medusa.ts`):

| Mode | When | Effect |
|------|------|--------|
| **DEMO** | `VITE_MEDUSA_BACKEND_URL` / `VITE_MEDUSA_PUBLISHABLE_KEY` / `VITE_STRIPE_PUBLISHABLE_KEY` unset or backend unreachable | Static catalog from `catalog.ts`, local cart, **simulated receipt**. No backend call. |
| **LIVE** | Those 3 vars set **and** backend reachable | Probes `/store/regions` + `/store/products`, **merges live Medusa variant IDs into the static catalog**, real carts + Stripe PaymentIntents + real orders. |

> **Important framing:** today the storefront is a **single men's ASCEND catalog at `/`**
> with exactly 4 products. The planned **dual sub-brand routing `/ascend` (men's) +
> `/glamgirl` (women's) is NOT yet implemented in code** — `app/src/App.tsx` has a flat
> router (`/`, `/product/:handle`, `/regimen`, `/privacy`, `/terms`, `/checkout`,
> `/confirmation`). The dormant research catalog in `app/src/data/products.ts` already
> carries both brands (`STORES.maxxed` → the men's set, `STORES.beauty` → the women's set),
> which maps onto the future `/ascend` + `/glamgirl` split. This playbook covers swapping
> the catalog today; the sub-brand routing is flagged where it will matter.

## 1. The swap surface — what a "product set" touches today

To swap a product set you must keep these **six locations in sync**. They hold the same
products under the same **canonical handle**:

| # | Surface | File / location | What lives there | Keys that must stay in sync |
|---|---------|-----------------|------------------|------------------------------|
| 1 | **Backend catalog** | `app/medusa-backend/src/scripts/seed.ts` | The `PRODUCTS` array: `title`, `handle`, `description`, AliExpress sourcing IDs, `price` (**integer cents**), three AliExpress CDN `images` (id strings). Seeding wires region / sales channel / publishable key / stock / fulfillment / shipping. | **`handle`**, `price` (cents), AliExpress `aliexpress_product_id` |
| 2 | **Storefront static catalog** | `app/src/lib/catalog.ts` | `CATALOG: StoreProduct[]` — the source of truth the UI actually renders. `handle`, `title`, `shortName`, `tagline`, `description`, `imageAlts`, `benefits`, `protocol`, `specs`, `price` (**cents**), `images` (local `/images/ascend/*.jpg` brand shots), `aliexpressProductId`. | **`handle`**, `price` (cents), `images`, `aliexpressProductId` |
| 3 | **Dormant research catalog** | `app/src/data/products.ts` | The 16-product research pool: `BEAUTY_PRODUCTS` (8, women→`/glamgirl`) + `MAXXED_PRODUCTS` (8, men→`/ascend`), each with `medusaHandle`, `price` (**dollars, not cents**), `image` → `/images/*.jpg` (research set), `viral`/`painPoint`/`saturation` grades, `sourceUrl`. This is the **candidate origin** for "test until a hit". | `medusaHandle` (currently differs from live handles) |
| 4 | **Product images** | `app/public/images/` (research set: `heatless-curler.jpg`, `height-insoles.jpg`, …) + `app/public/images/ascend/` (brand shots `<handle>-N.jpg`) | Storefront display images. Catalog `images` refs `/images/ascend/<stem>.jpg`. Generated by `app/scripts/generate-images.mjs`. | `stem` naming (`<handle>-1…N.jpg`) |
| 5 | **SEO / swap points** | `app/src/lib/seo.ts` (`SITE_URL`, `DEFAULT_OG_IMAGE`), `app/index.html` (hardcoded meta/`og:image`/JSON-LD), `app/public/sitemap.xml`, `app/public/robots.txt` | Canonicals, og tags, JSON-LD, sitemap `<loc>`s. | product `handle` in sitemap `<url>` blocks + PRD `og:image` |
| 6 | **Prerender routes** | `app/scripts/prerender.mjs` → `ROUTES` | Post-build bakes each route's rendered HTML into `dist/`. | product routes `/product/<handle>` |

**The single controller of what lands on the page is `catalog.ts` (#2).** REST mode and
LIVE mode both render from `CATALOG` (LIVE just overlays each product's live `variantId`).
Everything else mirrors it.

### The money rule (do not confuse the two price units)
- `seed.ts` + `catalog.ts` → **integer cents** (`3999` = $39.99).
- `products.ts` research pool → **dollars** (`24.99`). **Convert** when promoting (×100).
- `Medusa` API returns `amount` in cents — matches `catalog.ts` (`price`). The PDP renders
  `formatMoney(product.price)` (divides by 100), so keeping cents consistent is what makes
  LIVE and DEMO display the same price.

## 2. Backend path — replace a product set in `seed.ts`

`seed.ts` lives at `app/medusa-backend/src/scripts/seed.ts`. It is **idempotent** by
`handle`: `existingHandles` is built from all products, and only those whose handle is
**not already present** get created (`PRODUCTS.filter((p) => !existingHandles.has(p.handle))`).

### 2a. Exact commands (run from `app/medusa-backend/`)

```bash
cd "C:/Ascend Ecom/app/medusa-backend"

npm run build        # medusa build         → compiles modules/loaders
npm run migrate      # medusa db:migrate    → apply schema migrations
npm run seed         # medusa exec ./src/scripts/seed.ts
```

Prereqs before any of this: **Postgres + Redis up**, `DATABASE_URL` / `REDIS_URL` set in
`medusa-backend/.env` (loaded via `loadEnv` in `medusa-config.ts`). If the DB or Redis is
down, `seed` will fail loudly — don't paper over it.

`npm run start` (or `develop`) then serves the running backend.

### 2b. How pricing / descriptions / handles map

Each `PRODUCTS` entry requires, minimally:

```ts
{
  title: "EDGE — Jawline Exerciser",          // display title
  handle: "edge-jawline-exerciser",           // THE join key — see §3
  description: "...",
  aliexpress_product_id: "3256812532892500",  // supplier product id
  aliexpress_alt_product_id: "1005012719207252",
  aliexpress_item_url: "https://www.aliexpress.us/item/3256812532892500.html",
  price: 1499,                                // INTEGER CENTS
  images: ["Sc9af0cf06d934dbd85e27a14c15be0e8r", ...], // AE CDN id strings
}
```

- **Price** is passed straight to the variant's `prices: [{ currency_code: "usd", amount: p.price }]`
  → keep it integer cents. This is what the Stripe PaymentIntent and the merged storefront
  line price are charged.
- **Description** goes to the Medusa product record (visible in admin, in email/API,
  anywhere the backend originates copy). The storefront PDP renders its **own** copy from
  `catalog.ts description` — the two are edited separately.
- **Handle** must be slug-safe, unique, and **identical** to the `catalog.ts` handle.
- `manage_inventory:false` + `allow_backorder:true` (dropship) — keep these flags; stock
  lives at the supplier.
- Image `id`s become `IMG(id)` → `https://ae-pic-a1.aliexpress-media.com/kf/{id}.jpg`
  (hot-linked AliExpress CDN). These are used **for the backend product record only** —
  the storefront displays `catalog.ts` local brand shots instead. Both image sets must be
  filled for a full swap.

### 2c. CRITICAL idempotency caveat — seed does **not** update existing handles

Because `seed.ts` **skips any handle already present**, editing `price`/`description`/
`images` on an *existing* handle and re-running `npm run seed` will **silently do nothing**
for that product (it logs "Products already seeded — skipping."). To change an existing
product's price or copy you must either:

1. **Delete the old product** first (Medusa Admin UI or a `DELETE /admin/products/:id`),
   then re-run seed to recreate it under the same handle; **or**
2. **Use a new handle** (e.g. `edge-v2-jawline-exerciser`) and mirror it through catalog.ts,
   prerender, sitemap.

Do NOT assume a `seed` re-run updates live data. For a *swap-out* that replaces the whole
set you will typically delete the outgoing products in admin, edit `PRODUCTS`, re-migrate +
re-seed.

## 3. Storefront path — point `catalog.ts` at the new set

`app/src/lib/catalog.ts` is the single source the React tree renders. A `StoreProduct`
entry needs all fields present for the PDP/Home/Cart to work (see the live entries for the
shape): `handle`, `title`, `shortName`, `tagline`, `description`, `imageAlts[]` (same length
as `images[]`), `benefits[]`, `protocol[]`, `specs[]`, `price` (cents), `currency`, `images[]`
(`/images/ascend/<handle>-N.jpg`), `aliexpressProductId`.

**Handles and prices must match `seed.ts` exactly.** This is what makes the LIVE merge work:
`probeBackend()` in `app/src/lib/medusa.ts` does:

```ts
const live = productsRes.products.find((lp) => lp.handle === p.handle)
const variantId = live?.variants?.[0]?.id
return { ...p, variantId, live: Boolean(variantId) }
```

i.e. it fetches `/store/products?limit=50&fields=handle,variants.id` and matches on `handle`
only. There is **no alias mechanism** — the backend handle and the catalog handle must be
byte-for-byte equal. Consequences:

- **Handle mismatch** → `variantId` stays `undefined`, `live:false`. The product still
  renders and can be added to the local cart, but `createCart()` throws
  `Product <handle> is not available live.` → the **checkout fails** in LIVE mode.
- **Handles must be shared across `seed.ts`, `catalog.ts`, `prerender.mjs` ROUTES,
  and `sitemap.xml`.**

### Activating candidates from the research pool

`app/src/data/products.ts` is **dormant by design** — nothing imports `STORES` in the
current app. Use it as the **candidate origin**, not a runtime catalog. To test a candidate
from the pool:

1. Copy the candidate's `sourceUrl` + AliExpress IDs and confirm the AE listing (sourcing).
2. Rename to a clean **ASCEND handle** (the pool `medusaHandle` values like
   `height-insole-system` differ from the live `lift-height-booster-insole` — pick ONE
   canonical handle and use it everywhere).
3. Convert `price` dollars → cents (×100) in both `catalog.ts` and `seed.ts`.
4. Replace the pool's `image` (`/images/height-insoles.jpg`, research look) with branded
   `/images/ascend/<handle>-N.jpg` shots (regenerate via
   `node --env-file=.env scripts/generate-images.mjs <handle>` from `app/`).
5. Write ASCEND-voice `description`/`benefits`/`protocol`/`specs` + `imageAlts` to `catalog.ts`;
   write `description` + AE image ids to `seed.ts`.
6. Delete/leave the pool entry alone — it is a ledger of tested-vs-untested candidates.
   Annotate promoted vs. rejected there (see §4).

> Keep the count renderable: `Home.tsx` shows `live.products.length INSTRUMENTS` (dynamic,
> no change needed), but the **hero copy, `index.html` meta, and `seo.ts` are hardcoded to
> "four tools"** — bulk-copy about "Four precision looksmaxxing tools" goes stale if your
> swap changes the count. Update `app/index.html` `<meta>`/`og:description`, `Home.tsx` hero
> paragraph, and the `<noscript>` block when the set size or identity changes.

## 4. The "test-until-a-hit" loop (end-to-end)

The operator loop: promote candidates → verify → ship a rebuild → measure → keep (re-seed)
or roll back. DEMO mode is the fast, free way to iterate copy/framing; LIVE mode is the
trusted way to validate the backend merge + checkout. Do **both** — they exercise different
code paths.

```text
[1] Pick candidate   [2] Promote to catalog.ts + seed.ts   [3] Build
   (from products.ts)    (handles+cents+images in sync)        (tsc + vite + prerender)
        ^                                                        |
        |                                                       [4] Verify DEMO (static)
        |                                                        |   + LIVE (backend merge)
   keep / roll back                                             [5] Measure
```

### Step 1 — Pick candidates
Filter `products.ts` through the verifier v1 gate (§5). Prefer low `saturation`,
high `painPoint`/`viral`. Keep the set small to start (a 4-product product set, or promote
toward the 15–16 target on the women's side once sub-brands exist).

### Step 2 — Promote (edit the 6 surfaces)
Edit **only** `seed.ts` + `catalog.ts` + `prerender.mjs` ROUTES + `sitemap.xml` (+ imagery +
hardcoded copy) so every surface lists the new handles. Keep old handles in `seed.ts` only
until you've confirmed the swap, or delete them to hard-replace (see §2c).

### Step 3 — Build (from `app/`)
```bash
cd "C:/Ascend Ecom/app"
npm run build        # = tsc -b && vite build && node scripts/prerender.mjs
```
The build runs the prerenderer automatically (it needs `dist/index.html`, which `vite build`
just made). If prerender fails, the build fails — don't ship it.

### Step 4 — Verify locally — **both** modes
```bash
# DEMO (no backend vars): Vite dev server on port 3000 (vite.config server.port=3000)
npm run dev

# LIVE (backend vars set): build first, then preview the production bundle
npm run preview      # vite preview (default http://localhost:4173)
```
Checks, in order:

1. **Catalog renders** — Home shows the right number + handles; each PDP `/product/<handle>`
   exists.
2. **Inspect dist HTML** — `dist/index.html`, `dist/product/<handle>/index.html` should
   contain your new product's real `<title>`, meta description, `og:image`, canonical, and
   Product JSON-LD (the prerenderer captured them — grep for the new handle):
   ```bash
   rg -l "edge-jawline" "C:/Ascend Ecom/app/dist"     # or your new handle
   ```
3. **Both sub-brand routes** — until `/ascend` + `/glamgirl` are implemented, the flat
   `/` + `/product/:handle` are the routes to verify. When sub-brands land, verify each
   brand root and each PDP renders its own set (the catalog/products.ts `STORES` split maps
   to these paths).
4. **LIVE merge** — with the backend up and 3 env vars set, open preview; check the network
   tab for `GET /store/products?limit=50...` succeeding, and that checkout reaches Stripe
   (`initiateStripePayment` returns a `client_secret`) and `completeCart` produces an order.
   Any handle that fails to merge will fail here as `not available live`.
5. **Image check** — every `/images/ascend/<handle>-N.jpg` on each PDP returns 200; no 404s.

> **Pointer on LIVE + dev preview/CORS:** Vite dev runs on **3000**, `vite preview` on
> **4173**, but `medusa-config.ts` CORS `storeCors` defaults to `http://localhost:5173`.
> For LIVE-mode testing set `STORE_CORS` in `medusa-backend/.env` to include your dev/preview
> origin (e.g. `http://localhost:4173,http://localhost:3000`), otherwise `fetch` from the
> storefront to the backend is blocked and `probeBackend` silently degrades to DEMO.

### Step 5 — Measure, then keep or swap
Measure **per product set / per product** on sales + engagement (revenue in Stripe, order
records in Medusa, cart-adds in analytics or a smoke check):

- **HIT (keep):** leave in `catalog.ts`; make sure the backend is permanently seeded with
  the corresponding `seed.ts` entries so LIVE works against persisted products. Run the
  §2c delete/recreate step if the price changed on an existing handle.
- **MISS (swap out):** revert `catalog.ts` (restore the prior committed set), rebuild
  (`npm run build`), reseed backend to the kept set. Archive the losing candidate in
  `products.ts` with a `status: "rejected"` annotation + reason.

**Third-party tracking note:** there is **no analytics SDK** in the storefront `package.json`.
"Measure engagement" today means reading orders (Medusa/Stripe) and doing a manual/test-loop
smoke check (cart-add + checkout reach per set). Stand up real analytics before spending on
traffic.

**Sequence guard:** in LIVE, the catalog is static too — the backend only supplies
`variantId`s. If you change `seed.ts` but NOT `catalog.ts`, the home page/PDPs still show the
old products (they merge by handle); the new backend products simply aren't surfaced. To make
new products visible you MUST edit `catalog.ts`. In DEMO, the merge never happens and only
`catalog.ts` matters.

## 5. Pitfalls & guardrails

| Pitfall | Guardrail / fix |
|---------|-----------------|
| **Handle mismatch breaks the LIVE merge.** Catalog handle ≠ backend handle → `variantId` missing → checkout throws `not available live`. | Keep ONE handle across `seed.ts`, `catalog.ts`, `ROUTES`, sitemap. No alias layer exists. |
| **`seed` doesn't update existing handles.** Re-running seed after editing a price on an existing handle is a silent no-op. | Delete the product (admin/API) or use a new handle, then re-seed. |
| **Left-image / asset 404s.** `imageAlts` length must equal `images[]` length; a missing file → broken PDP gallery and og:image. | Generate all shots via `generate-images.mjs`; grep dist for each `images/ascend/*.jpg`. |
| **Stale prerender dist.** Pre-rendered HTML for a removed product lingers; new URLs absent. | Always `npm run build` (runs prerender) after any catalog change; never hand-edit `dist/`. |
| **Forgot to bump sitemap / prerender ROUTES.** Old product stays indexable, new one isn't; or prerender fails on the new route. | Add/remove matching `/product/<handle>` in BOTH `ROUTES` and `sitemap.xml` in the same change as `catalog.ts`. |
| **Removing a product referenced elsewhere.** A handle deleted from `catalog.ts` that's still in a cart (`[localStorage "ascend_cart_v1"]`), a hardcoded link, hero copy, or `seo.ts DEFAULT_OG_IMAGE`. | Sweep for the old handle with `rg "<old-handle>" app/src app/public app/scripts`. Update `seo.ts DEFAULT_OG_IMAGE` if you remove the current default image product. |
| **Hardcoded "four tools" copy drift.** `Home.tsx` hero, `index.html` meta, `<noscript>`, `seo.ts` all hardcode the 4-product men's set. | Update them when the set size/identity changes. Don't rely on the dynamic `INSTRUMENTS` count alone. |
| **Both price units in play.** `products.ts` is dollars, `seed.ts`+`catalog.ts` are cents. | Convert ×100 on promotion; keep `amount` in cents end-to-end. |
| **>50 products in Medusa.** `probeBackend` fetches `/store/products?limit=50` — a catalog beyond 50 products stops merging. | Batch `limit` or paginate if you grow past 50 live products. |
| **Backend unreachable in LIVE mode.** If any live fetch throws, `probeBackend` catches and returns `live:false` — you're back in DEMO without knowing it (a checkout that should be real is a simulation). | Set `STORE_CORS` for your dev/preview origin (see §4 pointer); watch the network tab; confirm `live:true` in a debug readout. |
| **Two image sources.** Backend uses hot-linked AliExpress CDN ids; storefront uses local `/images/ascend`. Both must be filled. | Add AE image ids to `seed.ts` AND local brand shots to `catalog.ts`. |
| **Supplements / topical / injectables creep in from the research pool.** | QC gate below. Fixetta sells **tools only** — nothing chemical, ingestible, or a topical formula at any point in the funnel. |

### Verifier v1 acceptance QC (`C:/Ascend Ecom/verifier/v1/criteria.md`)
Before a product swap ships, every landing product must clear:
- **Sell price > $20** (TikTok-shop typical). ⚠️ The current live men's set violates this:
  `frame-structure-shoulder-pads` = **$19.99** and `edge-jawline-exerciser` = **$14.99**. If
  you QC against v1, either reprice (>$20) or swap those two out — flag for the manager
  before going live on this gap.
- **Gross margin multiple ≥ 5×** (sell / AliExpress source cost).
- **No chemical / ingestible / topical-formula products** — tools only (no serums,
  supplements, creams, lash glue). Adhesive shoulder pads are physical, but anything with an
  active-chemical claim is a hard no.
- **≥ 15 products total** at the end (the women's `/glamgirl` candidates push toward this).
- Graded on viral ability / pain-point strength / saturation; each row has a direct AE link.
- Final deliverable is an `.xlsx` under `/mnt/agents/output/`.

### Operational guardrails
- **AliExpress fulfillment runs in QUEUE mode.** `medusa-config.ts` sets
  `ALIEXPRESS_MODE` default `"queue"`; `"live"` is only enabled with real API credentials
  (`ALIEXPRESS_APP_KEY`/`APP_SECRET`/`ACCESS_TOKEN`). **Until the owner confirms credentials,
  orders are queued + logged (supplier payload for manual processing / DSers import) — no
  real order is placed.** A product swap does not change this; it just changes what gets
  queued.
- **No ad spend.** There is a budget envelope — do not buy traffic. The "test-until-a-hit"
  loop is a **build + organic/verified-checkout smoke test**, not a paid acquisition test.
- **This playbook is a draft.** It does not publish or deploy anything. Deployment of any
  swap requires manager sign-off.
